# v1.31.0 通知可靠性三项收口

发布日期：2026-11-05

收口 v1.29.0 记录的三项未覆盖能力：持久化重试、按分组多规则接收人、独立投递历史页。
三条都围绕同一个问题：**值班能不能真收到、事后能不能查清。**

## 1. 重试持久化（重启续投）

- `notification_delivery` 新增 `pending` 状态与 `next_attempt_at`、`finished_at`、
  `duration_ms`、`updated_at`、`rule_id`、`rule_name`、`group_name` 等列。
- 告警派发先落库再尝试：首投失败后在退避期内由调度器（默认 5 秒一轮）原子领取续投。
  **待重试任务不在进程内**，网关重启后从表恢复，不需要人工重发。
- 第 `n` 次失败后的下次时间 = 当前时间 + `retry_backoff_seconds × 2^(n-1)`；
  达到通道 `max_attempts` 后终态 `failed`，`next_attempt_at=NULL`，`error` 可见。
- 去重键：`notification_delivery.id` 通过 `X-Vikings-Delivery-Id`（Webhook）或确定性
  `Message-ID`（SMTP）下发给接收端；语义为 **at-least-once**。网关用租约 + 状态机
  避免并发重复；若进程在 HTTP 已发出、结果未写回时崩溃，重启后仍可能重发同一条，
  接收端应按该 ID 幂等。
- 慢接收端不会占住数据库连接：一次尝试拆成「读取 → 网络请求（不持连接）→ 写回」三段，
  同时最多 3 条派发在跑，其余排队且不占连接，MQTT 上报不被拖慢。

## 2. 按分组配置接收人（多规则）

- 新增 `notification_rule` 表：每条规则独立配置名称、优先级、级别门槛、分组范围、
  设备白黑名单、Webhook URL/密钥、邮件收件人；SMTP 服务器/口令沿用全局配置。
- 裁决：`priority ASC, id ASC` 取**第一条**同时满足级别/分组/白黑名单的启用规则，
  命中即用其接收人，不叠加群发。界面按同一顺序展示。
- 未命中任何规则：**不投递**，记 `suppressed / channel=rule / 未匹配任何通知规则（设备分组: X）`。
  理由：避免未分类设备被误发给默认值班人，同时让「为什么没发」可在历史页回答。
  需要兜底时显式加一条 `groups` 为空的高优先级数字规则即可。
- 分组按设备**当前** `group_name` 实时判定：设备改分组后下一条告警立即命中新规则。
- v1.29.0 升级自动回填一条 `priority=100` 的默认规则，保持既有行为；
  规则表为空时运行期回退旧单配置行为。

## 3. 独立投递历史页

- 新增 `/notifications` 页面（不塞在系统设置里），菜单「投递历史」。
- 筛选：时间范围、通道（Webhook / 邮件 / 静默 / 规则）、状态
  （`pending` / `sent` / `failed` / `suppressed`）、设备 ID；服务端分页，前端不做二次过滤。
- 展示：尝试次数、累计耗时、最后错误、下次重试时间、命中规则与设备分组。
- 权限：`operator` 与 `admin` 可看，`viewer` 403。理由：错误信息含接收端基础设施线索，
  属运维信息；但值班人员需要不进系统设置即可确认告警是否发出，因此不收紧到 admin。

## 4. 未破坏既有语义

- 静默窗口（`mute_minutes`，同设备同指标抑制）与入库去重（`ALERT_SUPPRESS_SECONDS`）
  仍是两层独立机制：静默只阻止通知，不影响告警入库与实时推送；历史页以
  `channel=mute` 区分。
- 通知仍为旁路 `asyncio.create_task`，不阻塞 MQTT 消费。

## 5. 验证（真实环境，不 mock）

真实 PostgreSQL + 真实 uvicorn 网关 + 真实 mosquitto + 真实本地 HTTP 接收端，

| 优先级 | `priority` 升序首条命中；删除兜底规则后不再兜底 |

回归：gateway `pytest`、`flutter analyze`、`flutter test`、web `npm run test` / `npm run build`、E2E 全部通过（详见 CI）。

## 6. 升级说明

- 迁移：`alembic upgrade head`（`0007_notification_rules_retry`）。
- 既有配置升级后自动生成「默认规则（迁移自 v1.29.0 配置）」；如需按分组分流，
  在 Web「系统设置」新增规则后删除/调整默认规则即可。
- Downgrade 会移除规则表与 v1.31.0 新增列，**不会删除**既有 `notification_config` 与
  `notification_delivery` 数据；降级前请导出投递历史以便保留排障记录。
- 无破坏性 API 变更：旧配置端点与投递端点均保留，投递端点响应升级为分页对象。
