# v1.19.0 发布说明

- 发布日期：2026-11-05
- 提交：本提交（附注标签 `v1.19.0` 指向该提交）
- 标签：`v1.19.0`
- 对应交付项：`docs/delivery-readiness.md` 的 **P1-3（无正式迁移机制）** 与
  **P1-2（数据生命周期与备份恢复）**，合并为「数据层」一个版本

## 版本定位

一句话：**生产已经有数据的情况下，表结构变更和备份都变成可重复、可回滚的动作。**

本轮不改业务功能、REST 契约与 MQTT 报文格式，只补齐数据层基础设施：

- Alembic 迁移基线：空库建表、既有库自动标记（不重建）、降级可往返；
- 启动路径移除 `create_all` 与手写补列，生产启动只校验 schema 版本；
- 生产编排新增 `migrate` 一次性服务，迁移失败不启动网关；
- 告警/审计查询索引（有真实 `EXPLAIN` 证据）；
- records / 已确认告警 / 审计日志三套保留策略 + 手动清理入口；
- `pg_dump` 备份脚本（压缩、按时间命名、保留 N 份、失败非零退出）与恢复脚本；
- 隔离库真实恢复演练与 CI 的 PostgreSQL 作业。

## 只读核对结论（改动前）

| 项 | 改动前现状 | 本轮处理 |
| --- | --- | --- |
| 建表方式 | `database.py` 启动 `create_all` + `_migrate_columns` 手写补 `group_name` 与 5 个 `mqtt_*` 列 | 全部删除，结构只由 `gateway/alembic/versions/` 表达 |
| 生产初始化 | `infra/postgres/init.sql` 首次初始化建表并种 4 台演示设备 | 生产不再挂载；空库由 baseline 建表（无演示数据） |
| 告警索引 | 只有 `created_at`、`(device_id, metric, created_at)` | 新增 `(status, created_at)`、`(level, created_at)`、`(status, device_id)` |
| 审计索引 | `created_at`、`(action, created_at)` | 新增 `(operator, created_at)` |
| 数据清理 | 只清 `sensor_record`（90 天，按 `ts`） | 保留 records 口径；新增 acked 告警 180 天、审计 365 天；open 告警永不清 |
| 清理触发 | 仅进程内定时循环 | 定时 + `python -m app.maintenance purge [--dry-run]` 手动触发 |
| 备份 | 文档只有手工 `pg_dump` 命令 | 新增脚本（compress/retention/非零退出）与恢复脚本（确认保护） |
| CI | 网关只跑 SQLite pytest | 增加空库迁移步骤 + 真实 `postgres:16` 作业 |

## 数据库升级方式（生产）

### 常规升级

```bash
./scripts/pg_backup.sh --keep 30          # 1. 先备份
git fetch --tags && git checkout v1.19.0
./scripts/prod_up.sh                      # 2. migrate 自动 upgrade head
docker compose -f infra/docker-compose.prod.yml --env-file infra/prod/.env logs migrate
docker compose -f infra/docker-compose.prod.yml --env-file infra/prod/.env exec -T postgres \
  sh -c 'psql -tAc "select version_num from alembic_version" -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

`migrate` 退出码非 0 时 gateway 不会启动（`service_completed_successfully`）。

### 已有库（v1.18.0 及更早）

baseline 迁移探测到 `device` 表后**只记录版本、不重建**，日志输出：

```
[baseline] 检测到既有 schema，跳过建表，直接标记为已应用
```

也可显式判定后标记：`$COMPOSE run --rm migrate alembic stamp 0001_baseline`，
再 `upgrade head`。完整流程见 `docs/operations.md` 第 4 节。

### 回退

`alembic downgrade -1` 可回退最近一步并再次 `upgrade head` 往返；
**禁止生产执行 `downgrade base`**（baseline 的 downgrade 会删全部业务表）。
结构回滚以恢复升级前 `pg_dump` 为主。

## 迁移文件

| Revision | 内容 |
| --- | --- |
| `0001_baseline` | v1.18.0 及之前的 8 张表与索引；已有库自动识别跳过建表 |
| `0002_lifecycle_indexes` | 告警 3 个 + 审计 1 个查询索引，`downgrade` 逐个删除（先检查存在性） |

启动策略（`app/database.py::prepare_database`）：

- 开发/测试：自动 `upgrade head`，保留零配置启动；
- 生产：只校验 `alembic_version == head`，不一致拒绝启动，避免「代码新、库旧」；
- `create_all` 仅用于单元测试构造临时库，不再出现在启动路径。

## 数据保留口径

| 数据 | 默认 | 口径 |
| --- | --- | --- |
| `sensor_record` | 90 天 | 按上报时间 `ts` 删除，分块提交 |
| `device_alert` | 180 天 | **仅 acked**；open 永不自动删除（未处理欠账不能被悄悄清掉） |
| `audit_log` | 365 天 | 操作追溯依据、不可重建，因此比告警保留更久 |

配置项：`DATA_RETENTION_DAYS` / `ALERT_RETENTION_DAYS` / `AUDIT_RETENTION_DAYS` /
`DATA_PURGE_INTERVAL_SECONDS`；也可在 `GET /api/system/status` 的 scheduler 中查看。

手动清理（预检 + 执行）：

```bash
docker compose -f infra/docker-compose.prod.yml --env-file infra/prod/.env \
  exec -T gateway python -m app.maintenance purge --dry-run
docker compose -f infra/docker-compose.prod.yml --env-file infra/prod/.env \
  exec -T gateway python -m app.maintenance purge
```

## 真实验证结果

### Alembic

| 场景 | 结果 |
| --- | --- |
| 空库（SQLite）`upgrade head` | PASS，8 表 + 4 新索引，`version=0002_lifecycle_indexes` |
| 空库（PostgreSQL 16）`upgrade head` + `alembic check` | PASS，无结构漂移 |
| 既有库（模拟 v1.18：有表、无新索引、无 alembic_version） | PASS，日志「跳过建表」，存量 `dev-legacy` 数据保留 |
| 显式 `stamp 0001_baseline` → `upgrade head` | PASS |
| `downgrade -1` → `upgrade head`（SQLite 与 PostgreSQL 各一次） | PASS，索引删除后重建 |
| 事件循环内启动迁移（`prepare_database`） | PASS |

### 索引执行计划（真实 PostgreSQL，20 万告警 / 5 万审计）

| 查询 | 有索引 | 无索引（downgrade -1 后） |
| --- | --- | --- |
| `status='open' ORDER BY created_at DESC LIMIT 20` | `Index Scan using idx_alert_status_created` | `Index Scan using idx_alert_created`（首屏仍快） |
| 移动端角标 `status='open' AND device_id IN (...)` | `Index Only Scan using idx_alert_status_device`，2.48ms | 14.7ms（约 6 倍） |
| `level='critical' ORDER BY created_at DESC` | `idx_alert_level_created` 可用并被选中 | 回退到 `idx_alert_created` |
| 未处理总数 / 未处理严重数 | `Bitmap Index Scan`（status / level 索引） | 顺序扫描为主 |
| 审计 `operator='op-7'`（50 个操作人） | `idx_audit_operator_created`，0.037ms | 0.606ms（约 16 倍） |

### 保留清理（真实 PostgreSQL）

构造超期数据（400 天前 acked 3 条 / open 2 条、审计 2 条、records 2 条）后：

```
$ python -m app.maintenance purge --dry-run
待清理（仅统计，未删除）：{"records": 2, "alerts": 3, "audit_logs": 2}

$ python -m app.maintenance purge
已清理：{"records": 2, "alerts": 3, "audit_logs": 2}

$ SELECT count(*) FROM device_alert WHERE alert_id LIKE 'ev-open-%';
2      # 超期但未确认的告警被保留
```

## 偏差与取舍

1. **生产空库不再种入 4 台演示设备**：`init.sql` 只保留给本地开发编排；
   生产设备在首次上报时自动登记，或由管理员创建。这是把「schema 所有权」从 init.sql
   移到迁移文件的必然结果。
2. **生产不自动迁移**：启动只校验版本；迁移由 `migrate` 服务在部署流程执行。
   `docker compose up` 仍会自动触发该服务，因此日常操作步骤数不变。
3. **仅基线 downgrade 会删表**：正常回滚用 `downgrade -1` 或恢复备份；
   文档明确禁止生产 `downgrade base`。
4. **PostgreSQL CI 作业范围收敛**：只跑迁移与生命周期测试，不重复跑全量 pytest，
   把新增 CI 时间控制在约 1~2 分钟，避免变慢/变脆。
5. **索引取舍**：`idx_alert_status_created` 在 open 占比很小时被选中；
   当 open 占多数时优化器会选择 `idx_alert_created`（更快）。索引不是「强制命中」，
   报告给出两种分布下的真实计划，避免凭猜。
6. **审计日志清理不可逆**：默认 365 天；若合规需要长期留存，应在清理前导出归档。
