# v1.21.0 · 告警闭环：Web 批量确认、处置备注、级别口径统一

> 发布日期：2026-11-05
> 合并需求：P1-4（Web 复用批量确认）、P2-2（处置备注）、P2-1（级别口径统一）

## 版本定位

三项都围绕「告警处置体验」，合并交付以避免 Web 与移动端出现两套语义：

1. Web 后台不再逐条点确认，支持多选批量确认，**直接复用既有
   `POST /api/alerts/bulk-ack`**，没有新增第二套端点。
2. 告警确认从「只改状态」升级为「谁、何时、为什么确认」：
   `acked_by` / `acked_at` / `ack_note` 三列由 Alembic 迁移引入。
3. 级别口径收窄为规则引擎真实产出的 `warning` / `critical`，
   Web、移动端、契约文档同步收敛。

## 级别口径最终选择：收窄 (b)

规则引擎 `gateway/app/rules.py` 是确定性阈值引擎，只有「超阈值 → warning/critical」
一条分类路径，从不产出 `info` / `notice`。补齐这两级需要新的业务语义
（恢复通知、趋势提示等），属于新功能而非口径修正，且没有产品需求。
因此选择：

- 网关 `ALERT_LEVEL_PATTERN` 收窄为 `^(warning|critical)$`，查询传
  `info` / `notice` 返回 422；
- 移动端筛选只保留 `warning` / `critical`，未知级别回退灰显；
- Web 原本只有两级，无需改筛选；
- `docs/contracts.md` 写明最终枚举，并说明历史数据不存在这两级。

这样一次消除「页面支持四级但规则只产两级」的错位，风险最低。

## Web 现在能做到什么

- 告警列表首列多选，只有 `open` 行可勾选；已确认行不可选。
- 顶部「批量确认」按钮显示当前选中数；`viewer` 选中后按钮禁用，
  并展示「当前为只读账号（viewer），可以查看但不能确认告警」。
- 单条与批量确认共用同一个备注弹窗，备注可选（≤500 字）。
- 批量结果以常驻 `el-alert` 展示，逐类拆分：
  - `acked`：本次确认成功；
  - `already_acked`：此前已确认，保留原处置信息；
  - `not_found`：ID 不存在，失败可见。
  不再用一句「操作成功」掩盖部分失败。
- 列表新增「处置信息」列：确认人 + 确认时间 + 备注；
  历史已确认行显示「历史确认（无处置记录）」。

移动端保持同一语义：批量确认弹窗增加可选备注输入框，已确认卡片展示
确认人 / 时间 / 备注；级别筛选同步只剩两级。

## 处置字段与审计口径

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `acked_by` | varchar(64) NULL | 确认人（网关登录用户名） |
| `acked_at` | timestamptz NULL | 确认时间（UTC，单批共用一个时间戳） |
| `ack_note` | text NULL | 处置备注，API 限制 ≤500 字，空白归一到 NULL |

- 迁移 `0003_alert_ack_metadata` 只加可空列，不重建表、不修改既有行。
- **历史已确认行不回填**：无法得知真实操作人与时间，保持 NULL；
  不以 `created_at` 冒充 `acked_at`。
- **重复确认幂等**：`already_acked` 行不覆盖首次 `acked_by` / `acked_at` /
  `ack_note`，保证处置证据稳定。
- 审计动作仍为 `alert.ack`，批量时记录请求数与三类计数；
  备注只写 **脱敏后的 `note_summary`**（沿用 v1.20 `redact_text`，截断 100 字），
  Authorization/Bearer/口令键值不会原样进入审计或日志。

E2E 对本次改动的断言（脚本内逐项校验，任一项不满足即 FAIL）：

- 单条确认带备注后，REST 返回 `acked_by=<登录用户>`、非空 `acked_at`、`ack_note` 原文；
- 批量确认带备注，`acked` / `not_found` 逐类返回，部分失败可见；
- 查询 acked 列表，`acked_by` / `acked_at` / `ack_note` 与请求一致；
- 不带备注的重复批量确认返回 `already_acked`，再次查询备注仍未被覆盖。

E2E 使用真实 Broker、真实网关与真实 REST 链路，覆盖告警产生、筛选、确认、查询全流程。

## 兼容性

- `POST /api/alerts/{id}/ack` 的 body 变为可选；**不传 body 的旧客户端照常工作**。
- 批量确认新增 `note` 可选字段；旧请求体保持不变即可。
- `AlertOut` 只新增可选字段，旧客户端忽略即可。
- 级别查询由四值收窄为两值；规则引擎从未产出 `info` / `notice`，
  因此不存在需要迁就的历史行。若有外部脚本显式查询这两级，需同步改为
  `warning` / `critical`（契约已更新）。

## 偏差与遗留

1. **历史确认行无法补录处置信息**：字段保持 NULL；若业务需要回填，
   需新增「编辑处置记录」端点，而不是让重复确认覆盖首次证据。
2. **Web 未做 DOM 级多选测试**：vitest 覆盖 API 请求体与摘要拼装；
   多选交互由 Flutter widget 测试与 E2E 批量确认步骤覆盖（已在测试文件注释中说明边界）。
3. **级别收窄是破坏性契约变更**：外部若显式查询 `info/notice` 会收到 422；
   仓库内所有调用方（Web、移动端、E2E）已同步。
4. 批量备注为整批共用一条，不支持逐条不同备注；逐条差异场景走单条确认。
