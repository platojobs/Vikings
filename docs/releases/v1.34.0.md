# v1.34.0 · 可配置告警阈值规则

> 发布日期：2026-11-05
> 定位：把写死在 `gateway/app/rules.py` 的确定性阈值，变成一条条可管理、可审计、
> 可解释的规则。客户能按指标与范围自行调整阈值，改完即时生效；同时用默认规则种子
> 保证升级前后同一份数据的告警结果完全一致。

## 版本定位

- **阈值从代码搬到数据**：v1.33.0 的 10 个阈值（环境变量 + `rule_config` 覆盖）
  以 `is_default=True` 的默认规则写入 `alert_rule` 表，判定只读规则表；
- **行为不漂移**：默认规则范围 global、连续次数 1、比较方向与严格 `<` / `>`
  与 v1.33.0 完全一致，并用 36 组边界样本逐条对比证明；
- **仍只允许 warning / critical**：沿用 v1.21.0 收窄后的级别口径，不新增级别，
  避免与既有通知路由、SLA 时限、看板配色产生分叉；
- **可解释**：每条告警落 `matched_rule` 快照（规则 ID / 名称 / 方向 / 阈值 / 实际值），
  规则以后被改或删也不影响历史告警的“为什么触发”。

## 规则模型

| 字段 | 说明 | 取值 |
| --- | --- | --- |
| `name` | 规则名称（告警解释里展示） | 非空，≤64 字符 |
| `metric` | 指标 | `voltage` / `temperature` / `humidity` / `rssi` |
| `op` | 比较方向 | `lt`（低于阈值告警）/ `gt`（高于阈值告警） |
| `threshold` | 阈值 | 见下方指标合法区间 |
| `level` | 级别 | `warning` / `critical` |
| `scope_type` | 生效范围 | `global` / `group` / `device` |
| `scope_value` | 范围值 | `group` 填分组名，`device` 填设备 ID；`global` 为空 |
| `enabled` | 启用状态 | 停用后不再产生新告警，历史告警不变 |
| `consecutive_count` | 连续 N 次越限才触发 | 1~N，默认 1 |
| `priority` | 同级裁决顺序 | 数字越小越优先，默认 100 |
| `is_default` | 是否默认规则种子 | 影响“恢复默认阈值”与 `rule_config` 镜像 |

指标合法区间与允许方向（写入即校验，越界/反向直接拒绝）：

| 指标 | 允许方向 | 阈值区间 | 反向配置示例（拒绝） |
| --- | --- | --- | --- |
| `voltage` | 仅 `lt` | 2.0 ~ 4.5 V | 「电压高于 3.6V 告警」 |
| `temperature` | `lt` / `gt` | -40 ~ 85 ℃ | —（双向均合法） |
| `humidity` | 仅 `gt` | 0 ~ 100 % | 「湿度低于 40% 告警」 |
| `rssi` | 仅 `lt` | -150 ~ 0 dBm | 「信号高于 -80dBm 告警」 |

### 默认规则（v1.33.0 硬编码阈值的等价种子）

| 规则 | 指标 | 方向 | 阈值 | 级别 |
| --- | --- | --- | --- | --- |
| 电压过低-警告 | voltage | lt | 3.40 V | warning |
| 电压过低-严重 | voltage | lt | 3.20 V | critical |
| 温度过高-警告 | temperature | gt | 60.00 ℃ | warning |
| 温度过高-严重 | temperature | gt | 75.00 ℃ | critical |
| 温度过低-警告 | temperature | lt | -10.00 ℃ | warning |
| 温度过低-严重 | temperature | lt | -20.00 ℃ | critical |
| 湿度偏高-警告 | humidity | gt | 90.00 % | warning |
| 湿度偏高-严重 | humidity | gt | 97.00 % | critical |
| 信号过弱-警告 | rssi | lt | -100 dBm | warning |
| 信号过弱-严重 | rssi | lt | -110 dBm | critical |

种子读取 `rule_config` 的在线覆盖值（升级前在页面改过的阈值会被带入），没有则取
v1.33.0 的默认值；`gateway/app/config.py` 的默认值仍是“出厂值”，供“恢复默认阈值”使用。

## 裁决口径

**同一指标多条规则同时命中 → 取最高级别（critical 胜 warning），同级按
`priority` 升序、再按 `id` 升序，只保留一条。**

选择理由：

- 与 v1.33.0 的 `if critical else warning` 语义一致，迁移后同一数据不会多出告警；
- 告警抑制（`ALERT_SUPPRESS_SECONDS` 5 分钟窗口）、看板计数、移动端未读角标、
  SLA 与通知路由都以“一条告警 = 一个指标”为前提，全触发会让同一物理事件
  产生两条记录，既稀释统计也让值班人重复处置；
- “取首个”会让规则顺序成为隐性配置（调整顺序就可能改变结果），而 priority
  是显式字段，可审计可解释。

每条规则命中后，返回的 `matched_rule` 明确写出是哪一条规则胜出，因此“取最高级别”
不会丢失信息：被压制的低级别规则仍可在规则列表与审计里看到。

## 连续次数取舍

**只做“连续 N 次越限才触发”（`consecutive_count`），不做“持续 T 秒”。**

- 持续时长需要按时间窗缓冲上报并做定时回扫，会引入新的后台任务与状态存储；
  而 MQTT 上报本身有固定周期，N 次已能覆盖“抖动一次不算、连续异常才算”的绝大多数场景；
- 计数为进程内 `(device_id, 规则标识)` 计数：高频上报写计数表代价过大，
  代价是网关重启清零（最多延迟 N-1 次上报），与告警抑制同为进程内实现，
  文档已写明该边界；
- 一次正常上报即清零，避免“历史越限 + 偶发正常 + 再越限”被错算成连续。

## 缓存与热生效

**进程内全量缓存 + write-through 刷新。**

- 每次 MQTT 上报判定只读内存，不在热路径上查 `alert_rule` 表；管理端
  新增/修改/启停/删除/恢复默认后，服务层立即重载缓存，**无需重启**即可生效；
- 代价是只支持单实例网关：多实例时其它进程不会收到刷新（本项目当前部署为单实例）；
  若未来横向扩展，应改为按版本号轮询或在 Broker 上广播失效消息；
- 旧 `GET/PUT /api/rules/thresholds` 保留兼容：写入时同步更新对应默认规则行并
  镜像回 `rule_config`，因此旧客户端、脚本与 downgrade 回 v1.33.0 都不会丢阈值。

## 可解释与审计

- `device_alert.matched_rule`（JSON）：`rule_id` / `rule_name` / `op` / `threshold` /
  `level` / `value` / `consecutive`，MQTT `device/system/alert` 载荷新增同结构
  `matchedRule`；历史告警为 `null`，Web 显示“默认阈值（历史）”，不臆造规则；
- Web 告警列表「触发规则」列展示规则名与条件，hover 显示“由于 <规则>：<实际值> <方向>
  <阈值> 触发”；
- 审计动作：`alert_rule.create` / `alert_rule.update` / `alert_rule.enable` /
  `alert_rule.disable` / `alert_rule.delete` / `alert_rule.restore_defaults`；
  detail 只记规则名与**变更字段名**（`fields` / `changed_fields`），不记阈值数值。

## 权限与校验

| 角色 | 读规则 | 写规则（增/改/启停/删/恢复默认） |
| --- | --- | --- |
| 未登录 | 401 | 401 |
| `viewer` | 200 | 403 |
| `operator` | 200 | 403 |
| `admin` | 200 | 200 |

写入校验（全部返回 400 + 可读中文文案）：不支持的指标、级别不是 warning/critical、
方向与指标物理方向相反、阈值超出物理区间、NaN / 无穷大、`group`/`device` 范围缺值、
以及**同指标同范围下 critical 没有比 warning 更严格**（例如“低于 3.6V 算严重、
低于 3.4V 算警告”会让警告永远被压制，属于无效配置）。

## 偏差与说明

- 默认规则种子的 `priority` 使用 90（critical）/ 100（warning）：v1.33.0 的
  “critical 命中优先”本身就是级别优先，priority 只用于同级裁决，不影响结果；
- `matched_rule` 对 v1.34.0 之前的告警保持 `NULL`，Web 标注“默认阈值（历史）”，
  不用当前规则反推历史判定（规则可能已被修改）；
- 连续次数为进程内计数，重启清零；未实现“持续时长”，理由见上文取舍；
- 按指标物理方向拒绝反向比较，属于**在已知设备类型（电池电压、温湿度、RSSI）前提下的
  合理约束**；如果未来接入其它传感器，需要扩展 `METRIC_OPS` 与区间表。
